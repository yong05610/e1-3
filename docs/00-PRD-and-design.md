# Mini NPU Simulator — 요구사항 및 설계서

## 1. 문서 목적

이 문서는 mission.txt와 data.json을 기준으로 구현 범위, 프로그램 흐름, 함수 책임, 전체 단계와 완료 기준을 정의한다. 개발팀은 이 문서와 루트의 TASK.md를 기준으로 PM이 승인한 phase만 구현한다. 단계별 세부 지시서는 해당 phase를 시작할 때 작성한다. 이 문서와 mission.txt에 충돌이 있으면 mission.txt가 우선이며, 해석이 필요한 충돌은 임의로 결정하지 말고 PM에게 보고한다.

## 2. 제품 목표

Python 콘솔 프로그램으로 2차원 숫자 패턴과 필터의 유사도를 MAC 연산으로 계산한다. 사용자는 3×3 값을 직접 입력하거나 data.json의 사례를 분석할 수 있다. 프로그램은 점수, 판정, 성능 측정과 결과 요약을 제공한다.

학습자는 구현 결과를 통해 다음을 설명할 수 있어야 한다.

- MAC(Multiply-Accumulate) 연산과 점수 계산 원리
- 필터와 입력 패턴의 배열 표현
- data.json의 키·라벨 정규화 필요성
- 부동소수점 오차와 epsilon 동점 정책
- N×N 크기에서 MAC 연산량이 N²인 이유
- 데이터/스키마 오류, 로직 오류, 수치 비교 오류의 구분

## 3. 범위

### 필수 범위

- Python 3.8 이상, 표준 라이브러리만 사용한다.
- 제출 파일은 main.py, README.md이다.
- 크기 3×3, 5×5, 13×13, 25×25를 지원한다.
- 사용자 입력 모드: 필터 A, 필터 B, 패턴을 각 3×3 행렬로 입력한다.
- JSON 모드: 필터와 패턴을 로드하고 모든 패턴을 판정한다.
- 행렬 크기·행 길이·숫자 파싱 오류를 처리한다.
- JSON의 라벨을 Cross/X로 정규화한다.
- MAC 점수는 위치별 곱의 합으로 직접 계산한다.
- 점수 차이가 epsilon보다 작으면 동점 처리한다. 기본값은 mission.txt 권장값인 1e-9이다.
- 크기별 MAC 실행 시간을 10회 이상 측정하고 평균 ms와 N²를 표시한다.
- JSON 모드는 총 테스트/통과/실패 수와 실패 사례·사유를 출력한다.
- README에는 실행 방법, 구현 요약, 실패 원인 분석, 시간 복잡도 및 재현성을 기록한다. 결과 리포트는 최소 10줄 이상이다.

### 제외 범위

- 선택 보너스인 1차원 배열 최적화와 패턴 생성기
- NumPy, pandas 등 외부 라이브러리
- 그래픽 UI, 웹 서비스, 모델 학습
- 미션에 없는 추가 기능이나 구조 변경

## 4. 입력 데이터 계약

### 사용자 입력 모드

- 필터 A, 필터 B, 입력 패턴은 각각 3행이며 각 행은 공백으로 구분된 숫자 3개다.
- 잘못된 행/열 수나 숫자 파싱 오류는 안내 후 해당 입력을 다시 받는다.
- 두 필터 점수는 A/B로 표시하고, epsilon 동점이면 판정 불가로 표시한다.

### data.json

- 최상위 속성: meta, filters, patterns
- filters에는 size_5, size_13, size_25가 있고, 각 크기마다 cross와 x 행렬이 있다.
- patterns의 키는 size_N_idx 형태이고, 각 항목은 input 2차원 배열과 expected 라벨을 가진다.
- expected의 +는 Cross, x는 X로 정규화한다.
- 필터 키 cross는 Cross, x는 X로 정규화한다.
- 키의 N을 이용해 size_N 필터를 선택한다.
- 필터·패턴 크기 불일치는 해당 케이스 FAIL과 사유로 처리하고 프로그램 전체를 중단하지 않는다.

### 현재 제공 data.json 확인 결과

- JSON에는 size_5, size_13, size_25 필터 세트가 있다.
- 각 세트에는 cross와 x 필터가 있으며, 크기는 각각 5×5, 13×13, 25×25이다.
- 패턴은 size_5_1, size_5_2, size_13_1, size_13_2, size_25_1, size_25_2의 총 6개다.
- 미션의 출력 예시에는 8개가 나오지만, 예시는 참고용이며 실제 실행 총계는 제공된 data.json을 기준으로 동적으로 계산한다. 케이스 수 8을 하드코딩하지 않는다.

## 5. 사용자 흐름

1. 프로그램 제목과 모드 선택을 표시한다.
2. 사용자 입력 또는 data.json 분석 모드를 선택한다.
3. 선택한 모드에서 입력을 로드하고 검증한다.
4. Cross/X 또는 A/B 필터별 MAC 점수를 계산한다.
5. epsilon 정책으로 판정하고 결과를 표시한다.
6. 크기별 성능을 측정한다.
7. JSON 모드에서는 케이스별 PASS/FAIL 및 전체 합계를 표시한다.

## 6. 함수 구조와 호출 책임

프로젝트 규모에 맞춰 함수 중심의 단일 main.py로 구현한다. 클래스를 만들지 않는다. 함수가 늘어나거나 책임 분리가 더 명확해질 때만 PM 승인 후 구조를 바꾼다.

| 함수 | 책임 | 호출 관계 |
|---|---|---|
| main() | 메뉴 표시 및 선택에 따른 분기 | run_user_mode() 또는 run_json_mode() |
| read_matrix() | 지정 크기의 행렬 입력 및 행/열/숫자 검증 | run_user_mode() |
| load_data() | data.json 읽기와 JSON 오류 처리 | run_json_mode() |
| normalize_label() | 입력 표기를 표준 Cross/X로 변환 | run_json_mode() |
| validate_matrix() | 행렬의 정사각형 크기와 데이터 유효성 확인 | 두 모드 및 JSON 사례 처리 |
| mac() | 두 동일 크기 행렬의 위치별 곱의 합 | 두 모드 |
| classify() | 두 점수의 epsilon 비교 및 승자/동점 반환 | 두 모드 |
| benchmark_mac() | MAC 호출 구간을 반복 측정하고 평균 ms 반환 | 두 모드 |
| run_user_mode() | 사용자 입력 모드 실행 흐름 | read_matrix(), mac(), classify(), benchmark_mac() |
| run_json_mode() | JSON 모드 실행, 사례별 처리 및 결과 요약 | load_data(), normalize_label(), validate_matrix(), mac(), classify(), benchmark_mac() |

호출 관계 요약:

> main() → run_user_mode() 또는 run_json_mode()  
> 각 모드 → 입력/로드·검증 → mac() → classify() → 출력  
> 성능 출력은 benchmark_mac() 결과를 사용한다.

## 7. 수치·성능 정책

- MAC은 중첩 반복문으로 직접 계산한다.
- epsilon 기본값은 1e-9이며, abs(score_a - score_b) < epsilon이면 동점이다.
- 측정은 MAC 함수 호출 구간만 포함한다. 입력/출력/파일 읽기 시간은 제외한다.
- 각 크기는 최소 10회 반복 후 평균 ms를 출력한다.
- 표에 크기 N×N, 평균 시간(ms), 연산 횟수 N²를 포함한다.
- 시간 측정값은 컴퓨터 환경에 따라 달라지므로 예시 수치를 정답으로 하드코딩하지 않는다.

## 8. 오류 처리 원칙

- 사용자 입력 오류는 프로그램을 종료하지 않고 잘못된 입력을 다시 요청한다.
- JSON 전체를 읽을 수 없는 오류는 이해 가능한 오류 메시지로 안내하고 비정상 traceback을 사용자에게 노출하지 않는다.
- JSON 개별 사례의 키/행렬/크기 오류는 사례 단위 FAIL로 기록한 뒤 나머지 사례를 계속 처리한다.
- 실패 원인을 사례 ID와 함께 출력한다.
- 정상 비교 결과와 데이터 오류로 인한 FAIL을 구분해 기록한다.

## 9. README 산출 요건

- 실행 방법과 모드 선택법, data.json 위치
- 라벨 정규화 방식, MAC 반복문, epsilon 동점 정책
- 실제 JSON 분석 결과와 실패 사례 원인
- 결과가 0 FAIL일 경우에도 그 이유

- 크기 증가에 따른 O(N²) 근거
- 재현성 있는 입력 예시와 의도적 오류 처리 결과
- 결과 리포트는 최소 10줄 이상

## 10. 승인·진행 규칙

- 개발팀은 PM이 전달한 한 phase만 수행한다.
- 다음 phase 지시가 오기 전까지 후속 구현을 시작하지 않는다.
- 문서에 없는 요구, 상충하는 기준, 구현 선택이 필요한 사항은 코드 작성 전에 PM에게 질문한다.
- 완료 보고에는 변경 파일, 구현 내용, 직접 확인한 항목과 실제 결과, 미완료/주의 사항을 포함한다.
- PM은 개발 보고를 사실로 간주하지 않고 소스와 실행 결과를 독립 검증한 뒤 사용자에게 보고한다.
- TASK.md는 전체 단계와 현재 상태를 기록하는 단일 진행표로 사용한다.
- 각 phase 지시서는 사전에 모두 만들지 않는다. 사용자가 해당 phase 진행을 승인했을 때 PM이 그 단계에 필요한 지시서만 docs/에 작성한다.
- phase 통과 확인 전에는 TASK.md에서 완료 체크하지 않으며 다음 phase로 진행하지 않는다.

## 11. 전체 개발 단계

### Phase 1 — 핵심 계산

MAC 점수 함수와 epsilon 기반 동점/승자 판정 함수를 구현한다. 3×3 예시 점수 및 동점 기준을 확인한다.

### Phase 2 — 사용자 입력 모드

메뉴와 3×3 필터 A/B 및 패턴 입력, 행/열/숫자 오류 재입력, A/B 판정, 3×3 평균 시간 출력을 구현한다.

### Phase 3 — JSON 분석 모드

data.json 로드, 키 기반 크기 선택, 라벨 정규화, 사례별 크기 검증, PASS/FAIL 및 총계를 구현한다. 사례 오류가 전체 실행을 중단시키지 않게 한다.

### Phase 4 — 전체 성능 분석

3×3, 5×5, 13×13, 25×25의 10회 이상 평균 시간과 N² 연산 횟수를 표로 출력한다. I/O 시간은 측정에서 제외한다.

### Phase 5 — README 및 최종 통합

개발팀이 README를 작성하고 제출 기준을 통합 확인한다. 결과 리포트 10줄 이상, 실패 원인 분석 또는 0 FAIL 근거, 복잡도와 재현성을 포함한다. 완료 후 PM이 README와 코드·실행 결과를 독립 대조해 최종 수용 여부를 결정한다.
