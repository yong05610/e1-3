# Phase 3 — data.json 분석 모드

## 개발팀 지시서

먼저 docs/00-PRD-and-design.md, TASK.md, 앞선 phase 지시서와 보고서를 읽으세요. Phase 1과 2는 PM 검증을 통과했습니다. 이번 요청으로 승인된 범위는 Phase 3뿐입니다. 다른 phase 기능이나 보너스 작업은 구현하지 마세요.

### 목적

data.json의 필터와 패턴 사례를 읽어 각 사례의 MAC 점수·판정·expected 비교 결과를 출력하고 총계를 표시합니다.

### 이번 단계 범위

- 기존 사용자 입력 모드를 보존하고 메뉴의 JSON 항목에서 JSON 분석 모드를 실행하도록 연결합니다.
- data.json은 main.py가 있는 프로젝트 경로를 기준으로 찾아 읽습니다. 현재 작업 폴더가 다르더라도 파일을 찾을 수 있어야 합니다.
- 최상위 meta, filters, patterns 구조를 확인합니다.
- size_5, size_13, size_25 아래의 cross/x 필터를 읽습니다.
- pattern 키 size_N_idx에서 N을 안전하게 추출하고 해당 size_N 필터 세트를 선택합니다.
- expected 라벨 +는 Cross, x는 X로 정규화합니다. 필터 키 cross는 Cross, x는 X로 정규화합니다. 대소문자와 앞뒤 공백을 안전하게 처리합니다.
- Phase 1의 mac()과 classify()를 재사용합니다. 점수 계산과 판정 로직을 중복 구현하지 않습니다.
- 사례마다 Cross 점수, X 점수, 판정(Cross/X/UNDECIDED), expected, PASS/FAIL을 출력합니다.
- 판정이 UNDECIDED이면 expected가 Cross 또는 X라도 PASS가 될 수 없고 FAIL로 처리합니다.
- 키·라벨·행렬 구조·행/열 크기가 잘못된 개별 패턴은 사례 ID와 구체적인 실패 사유를 출력하고 그 사례만 FAIL 처리합니다. 다른 사례 분석은 계속합니다.
- 특정 크기의 필터가 없거나 손상된 경우 그 필터를 쓰는 사례를 FAIL 처리하고 계속 진행합니다.
- 정상적인 JSON 전체 파일을 열거나 파싱할 수 없는 경우에는 사용자가 이해할 오류를 표시하고 traceback으로 비정상 종료하지 않습니다.
- 총 테스트 수는 patterns에 실제로 존재하는 사례 수를 기준으로 집계합니다. 현재 제공 data.json의 6개 사례를 확인하되 6이나 미션 예시의 8을 코드에 하드코딩하지 않습니다.
- Phase 1/2의 메뉴와 사용자 입력 모드를 유지합니다.

### 이번 단계에서 하지 말 것

- 성능 측정, 3×3/5×5/13×13/25×25 성능표(Phase 4)
- README 작성과 최종 결과 리포트(Phase 5)
- data.json 원본의 값/기대 라벨 변경
- 자동 테스트 파일이나 프레임워크 추가
- 보너스 기능, 클래스 도입, 외부 라이브러리
- Phase 1의 epsilon 또는 MAC 동작, Phase 2의 사용자 입력 흐름 변경
- TASK.md의 상태 변경(PM 검증 뒤 PM이 갱신함)

### 완료 확인 기준

- 제공된 data.json을 실행해 현재 6개 모든 사례의 점수·판정·expected 비교를 출력합니다.
- Cross/X 표준 라벨이 출력되며 expected와 판정 비교가 정확합니다.
- 실제 케이스 수 기준으로 총/통과/실패가 계산되고 케이스별 결과 합과 일치합니다.
- 데이터 구조/크기 오류 사례는 FAIL 사유를 남기며, 그 뒤 정상 사례가 계속 처리됩니다.
- 잘못된 전체 JSON 파일은 사용자 친화적 오류로 안내되고 traceback 없이 종료됩니다.
- 기존 3×3 사용자 입력 모드의 정상, 동점, 재입력 흐름이 유지됩니다.
- JSON 모드에서 성능 표는 아직 출력하지 않습니다.
